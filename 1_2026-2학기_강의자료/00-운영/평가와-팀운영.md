# 평가와 팀 운영

## 성적 배분

| 항목 | 비중 | 평가 기준 |
|---|---|---|
| 주차별 실습 과제 (12회) | **25%** | 완성도보다 **"측정하고 정량화했는가"** |
| 중간 발표 (8주차) | **15%** | 전반부 데모 + Term Project 제안의 타당성·구체성 |
| Term Project 데모·성능 (15주차) | **35%** | 통합 성공률, 지표 달성도, 코드 품질 |
| 최종 보고서 | **15%** | 설계 근거, 결과 해석, 실패 분석의 논리 |
| 팀 기여도 (동료평가) | **10%** | 팀원 상호평가 + 커밋·이슈 기록 |

**중간고사 없음.** 필기시험 대신 8주차 중간 발표와 15주차 최종 데모로 평가한다.

## 채점의 원칙

> **실패한 실험도 원인 분석이 있으면 만점.**
> 성공했으나 측정하지 않은 결과는 감점.

- 근거는 [[측정하지-않은-성공은-성공이-아니다]] 에 정리해 두었다. 학생에게 1주차에 명시한다.

### 주차별 과제 채점 시 보는 것

| 볼 것 | 안 볼 것 |
|---|---|
| 지표를 정의했는가 | 코드가 예쁜가 |
| 조건과 반복 횟수를 적었는가 | 결과가 좋은가 |
| 그래프에 축 라벨·단위·범례가 있는가 | 분량이 많은가 |
| 실패 원인을 자기 말로 설명했는가 | 참고자료를 많이 달았는가 |

### 흔한 감점 사유

- 그래프에 단위가 없다
- "잘 동작했다"고만 쓰고 수치가 없다
- 1회 실행 결과를 결론으로 제시했다
- 남의 코드를 붙여넣고 왜 그런지 설명하지 못한다

## 팀 구성

**4~5명 × 3~4팀.** 팀장을 정한다.

| 역할 | 담당 |
|---|---|
| 인지 (Perception) | LiDAR·카메라 처리, 융합, 객체 라벨링 |
| 제어 (Control) | Simulink 제어기, 상태추정, LOS, DP |
| 시뮬레이션 (Sim & Model) | 월드·모델 수정, 파라미터, 배치 실험 |
| 통합 (Integration) | 미션 매니저, 로그 파이프라인, 문서화 |

### 역할 로테이션 — 11주차에 1회 강제

**"인지만 아는 학생", "제어만 아는 학생"이 생기는 것이 캡스톤디자인의 가장 흔한 실패다.**

- 11주차는 충돌회피를 시작하는 시점 — 인지와 제어가 처음 맞물림
- 이때 역할을 바꾸면 서로의 인터페이스를 이해할 수밖에 없음
- 로테이션 후 첫 주 생산성 저하는 감수함

## 미팅

| 대상 | 주기 |
|---|---|
| 팀 자체 미팅 | 주 1회 이상 |
| 지도교수 미팅 | 2주 1회 |
| 수업 중 팀 스크럼 | 매주 20분 (수업 끝) |

- 수업 중 스크럼에서 다루는 것
  - 지난주 결과 비교
  - 실패 원인 공유
  - Term Project 진척
- **"잘 되고 있습니다"는 보고가 아님** — 무엇을 몇 번 돌려서 어떤 숫자가 나왔는지 말할 것

## 협업 도구

| 용도 | 도구 |
|---|---|
| 코드 | GitHub Organization — 팀별 레포 |
| 문서·일정 | Notion 또는 팀 레포의 `docs/` |
| 소통 | 팀 채널 (질문 시 에러 메시지 전문 포함) |

- 동료평가 10%는 커밋·이슈 기록과 함께 본다. 커밋이 한 명에게 몰려 있으면 확인한다.

## 사양 미달 학생 처리

- 1주차 과제에서 노트북 사양을 신고받음. **신고에 불이익 없음**
- RAM 16 GB 미만 또는 4코어 미만이면 연구실 워크스테이션 원격 접속(SSH / NoMachine) 배정
- 숨기고 버티다 5주차에 이탈하는 것이 최악의 경로
- 배경: [[환경구축-실패가-가장-비싼-비용이다]]
